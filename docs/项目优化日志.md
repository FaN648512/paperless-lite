## 一、项目起点：一次「体检式」立项

### 1.1 动机

需要一个把**纸质票据、合同、报告**数字化后可搜索的本地文档库。业界标杆是 paperless-ngx，但直接部署在目标机器上存在硬阻碍：

| 体检项 | 实测结果 | 对 paperless-ngx 的影响 |
|---|---|---|
| 内存 | 3.9 GB（常态可用 0.3–0.5 GB） | ✗ 官方推荐 ≥ 2 GB 仅够单文档；多组件（Redis + Celery + Postgres + Tika + Gotenberg）根本起不来 |
| CPU | 2 核，2011 年 Pentium（**无 AVX2**） | ✗ 新版 onnxruntime / 部分 OCR 依赖直接崩溃 |
| 虚拟化 | Hyper-V / WSL / 容器能力**全部禁用** | ✗ 官方只支持 Linux + Docker，本机无法容器化 |
| 系统 | Windows 10 专业版 | ✗ 官方不支持 Windows 原生部署 |

### 1.2 做法：不走「跑不动就算了」，走「保真降级」

优先尝试按原项目文档跑通；确认硬阻碍不可绕过后，**保留核心玩法**做降级实现——四大核心一个都不能少：

```
图片/PDF/Excel/PPT 上传 → OCR 文本提取 → 标签（含自动规则引擎）→ 中文全文搜索
```

技术选型对照：

| 能力 | paperless-ngx 原方案 | 本项目降级方案 | 取舍理由 |
|---|---|---|---|
| OCR 引擎 | Tesseract（100+ 语言） | **RapidOCR（PP-OCRv4，onnxruntime）** | 纯 pip 依赖、无系统二进制、**中文票据识别优于 chi_sim** |
| 全文检索 | Postgres / SQLite + 多组件 | **SQLite FTS5 `trigram` 分词** | 单文件库、零外部服务；trigram 对中文子串检索友好 |
| 队列 | Redis + Celery | **进程内 `queue` + 工作线程** | 省掉两个常驻进程，内存预算内 |
| 前端 | Angular SPA | **原生 JS 单页 + 深色卡片 UI** | 无构建链，2 核机秒开 |
| 自动标签 | 机器学习分类器 | **规则引擎（any / all / 正则 / 全文）** | 小数据量下规则更可解释、可调试；不引入模型内存开销 |

### 1.3 作用与预期效果

- **作用**：在老硬件上完整复刻了「上传→OCR→标签→搜索」闭环，验证通过 27/27。
- **预期效果**：核心体验不打折（拒绝空壳页面）；后续若迁到公司服务器，只需换运行环境，**代码零改动**。

## 二、核心链路：上传 → OCR → 自动标签 → 中文搜索

### 2.1 双分支文本抽取

**动机**：票据大多是无文本层的扫描图，但合同/报告常带文本层。一律走 OCR 既慢又损精度。

**做法**：管线先探测 PDF 是否含文本层 ——

| 输入类型 | 处理分支 | 说明 |
|---|---|---|
| 图片（png/jpg/bmp/tif/webp） | RapidOCR 识别 | 输出带置信度的行文本，按阅读顺序拼接 |
| 扫描版 PDF（无文本层） | 逐页渲染 → RapidOCR | 页级进度回传，支持「处理中」状态 |
| 原生 PDF（有文本层） | PyMuPDF 直取文本 | **跳过 OCR，速度快一个数量级** |
| Excel / PPT | openpyxl / xlrd / python-pptx | 抽取单元格与幻灯片文本 |

**作用与预期效果**：把「一次上传」的最坏耗时从「全文 OCR」压到「有文本层就直取」，并让 OCR 只在真正需要时占用 CPU。

### 2.2 中文全文搜索：trigram 主路径 + LIKE 兜底

**动机**：中文没有空格分词，SQLite 默认分词器对中文子串几乎不可用；而 FTS5 的 `trigram` 分词器要求查询词 ≥ 3 个字符——搜索「发票」「合同」「收据」这类两字词会全部落空。

**做法**：查询词 ≥ 3 字走 FTS5 trigram（相关性排序 + 命中高亮），< 3 字自动回退 `LIKE`，两条路结果合并去重。FTS 表使用 `external content`（`content='documents'`）+ 触发器同步，避免正文重复存储。

**作用与预期效果**：覆盖「两字短词 / 三字词 / 长短语 / 数字金额 / 证件号 / 带标点日期」全部查询形态；在 2 核机上，全文检索保持**毫秒级**响应。三字词走主路径的性能优势实测明显。

### 2.3 自动标签规则引擎

**动机**：上传后手工打标签是重复劳动，而小数据量下又没必要上机器学习。

**做法**：规则 = 字段 × 匹配方式 × 模式串。

| 维度 | 可选值 | 说明 |
|---|---|---|
| 字段 | `any` / `title` / `content` / `correspondent` | 在哪儿找 |
| 匹配 | `any`（空格分词 OR）/ `all`（AND）/ `regex`（正则）/ `fulltext`（全文检索式） | 怎么算命中 |
| 附加 | 大小写敏感、启用开关、命中计数 | 便于排查规则为何没生效 |

新建标签时可自动生成规则，并**立即对全库执行一次匹配**，把已有文档补上标签。

**作用与预期效果**：新文档"落库即带标签"；规则可解释、可视化，标签体系变更时不用重跑模型。

## 三、交互补齐：详情面板 / 标签 / 批量导入 / Office 格式

| # | 需求 | 动机（用户痛点） | 做法 | 作用与预期效果 |
|---|---|---|---|---|
| 1 | 详情面板有关闭键、顶栏固定 | 面板内容长，滚动后关闭键跑没了 | 顶部工具栏 `position: sticky`，「×」按钮水平垂直居中，兼支持 `Esc` | 长文档阅读时随时可关，不丢操作入口 |
| 2 | 新建标签自动全库匹配 | 新标签只能管以后的文档，历史文档要手工补 | 建标签 → 生成规则 → 立即全库匹配 | 标签体系演进零维护成本 |
| 3 | 标签可删除 | 标签建错了没法收回 | hover 显「×」，删除时级联清理关联规则与文档关联 | 标签治理闭环 |
| 4 | 文件夹批量导入 | 一次几十份文件逐个上传不现实 | 输入路径 → 扫描 → 列表内可删改 → 确认导入；按 **MD5 查重**，重复文件只留一份并提示 | 大批量归档从"分钟级手工"变为"一次确认" |
| 5 | 卡片删除键 | 列表里清错文件要先进详情再删 | 每张卡片右下角直接给删除入口 | 减少两级跳转 |
| 6 | 扫描空结果弹窗 | 路径写错时静默返回空列表，用户以为卡死 | 扫描无结果显示明确弹窗提示 | 消除"没反应"的焦虑 |
| 7 | Excel / PPT 导入 | 台账、培训课件也是需要归档的正式材料 | 扩格式白名单 + 解析管线 + 左侧「格式分类」筛选（含数量统计） | 文档库从"票据专用"升级为"资料总库" |
| 8 | UI 细节（图标风格统一、格式栏两列、全部格式并入） | 单列按钮在高分屏下过窄/过长，图标风格不一致 | 统一线性风格图标；格式栏改 **一行两个**圆角按钮；「全部格式」并入两列并显示计数 | 视觉节奏统一，扫读效率更高 |

**批量导入的并发保护**（重要）：上传进度轮询最初是「每个 tick 每份文档一个请求」，在 2 核机上直接造成请求风暴拖垮服务。改为**单次列表请求 + 10 分钟兜底上限**后，界面依旧实时，机器不再打摆。

## 四、视觉规范：深色操作界面 与 护眼绿文档

**动机**：项目里并存两类 HTML，阅读诉求完全不同：一类是**长时间阅读的说明/教程**，一类是**高频操作的应用界面**。用同一套配色是错的。

**做法**：把颜色全部收进 `:root` CSS 变量，一处可换肤：

| 场景 | 配色 | 理由 |
|---|---|---|
| 应用界面（`static/index.html`） | 深色卡片式 | 操作性 UI，深底让缩略图与状态色更"跳"，长时间筛选不刺眼 |
| 说明 / 教程类 HTML | **护眼绿（豆沙绿）** | 中低明度黄绿色，亮度约 82%（纯白 100%），压掉高频蓝光；正文对比度仍达 8.9:1，超过 WCAG AA（4.5:1）要求 |
| 代码块 | 浅底 + 酒红 `#b3305c` | 浅色背景上比亮蓝更清晰 |

护眼绿变量：`--bg:#cfe6cd --panel:#e6f1e2 --card:#f4f9f1 --line:#b7cdb5 --text:#24342a --accent:#1f6e4e`

**作用与预期效果**：阅读型文档"看着不累"，操作型界面"看着清楚"；换肤只需改变量，不碰结构。改完用正则扫一遍硬编码颜色即可确认无深色残留。

## 五、从「单人本地」到「小团队内网共用」

### 5.1 动机

文档库要能坐落在同一间办公室的同事电脑上打开，但**绝对不能出现"零鉴权裸奔"的窗口期**——合同发票一旦被人随便翻，风险远大于便利。

### 5.2 做法：三道锁一次配齐

| # | 动作 | 关键实现 |
|---|---|---|
| 1 | 服务监听 `0.0.0.0` | 由环境变量控制（`PAPERLITE_HOST`），要退回纯本机就设 `127.0.0.1` |
| 2 | **全站鉴权** | `@app.before_request` 统一拦截；白名单仅 `/static/`、`/api/auth/`、`/login`；**未设密码 → 全部重定向到设置页**（无空窗期）；未登录 → 页面跳登录、API 返回 401 |
| 3 | 密码哈希存储 | `werkzeug` scrypt 哈希落盘到数据目录的 `auth.json`，session 密钥独立生成 |
| 4 | 防火墙按需放行 | `局域网共享.py` 一键「开放 / 关闭 / 查状态 / 排查」，规则限定 `profile=private,domain`（咖啡厅公网不算） |
| 5 | 防爆破 | 外部 IP 连错 5 次锁 5 分钟；**本机（127.0.0.1/::1）不锁** |

**为什么本机不锁**：自己手滑几次就被自己挡在门外，是典型的"安全设计伤害主人"。锁定的目的是挡外部探测，本机是可信终端。

**Windows 防火墙的坑**：`netsh` 在受限环境下会"退出码 0 但什么都不做"的静默失败，改用 PowerShell 的 `New-NetFirewallRule` 才真正生效（详见第九节）。

### 5.3 作用与预期效果

- 同事浏览器输 `http://<内网IP>:8765` → 输账号密码即可用；
- 安全验证 **32/32 全过**（弱密码拒绝、哈希非明文、未登录拦截、防爆破、本机不锁）；
- 明确了三条红线：**明文 HTTP 仅限公司内网**、**3.9 GB 内存不支持多人并发 OCR**、**绝不做内网穿透**。

## 六、从「一个账号」到「多用户 + 文档可见性」

### 6.1 动机

"我上传的文件想让谁看/让谁改"是共用文档库的刚需，但它成立的前提是——**系统必须记得每份文件是谁上传的**。没有归属概念，就无从谈权限。

### 6.2 做法

**数据层**：`documents` 表加 `owner`（上传者）与 `visibility`（可见性）两列；老库通过轻量迁移自动补列（`ALTER TABLE`），历史数据不丢。

**可见性三态语义**：

| 状态 | 别人能看 | 别人能改 | 适用场景 |
|---|---|---|---|
| 🔒 私密 `private` | ❌ | ❌ | 工资、个人合同 |
| 👁 只读 `readonly`（默认） | ✅ | ❌ | 制度文件、对外资料 |
| ✏️ 公开编辑 `public_edit` | ✅ | ✅ | 协作整理的项目资料 |

**权限判定**：仅 `owner` 或管理员可改可见性；编辑、删除、打标签、重识别一律按可见性放行；私密文档对其他人的**列表、搜索、候选词、缩略图、原件下载**全部不可见。

**前端**：详情面板顶部为可见性选择器；卡片显示归属徽章（如「👁 只读 · admin」）；不可编辑时按钮禁用并给出原因提示。

### 6.3 作用与预期效果

- 权限测试 **40/40 全过**；
- 预期效果：从"大家共用一个库、谁都怕被改"变成"各管各的文件、按需共享"；管理员可通过「用户管理」增删账号。

## 七、对标优秀项目后的能力升级（Top 3）

### 7.1 动机

闭门造车不如对标。调研了 6 个同类标杆，逐一拆解**核心优势 / 特色亮点 / UI 审美**：

| 项目 | 路线 | 核心优势 | 最值得借鉴的一点 |
|---|---|---|---|
| **paperless-ngx** | 社区旗舰 | 功能最全、交互打磨最细，权限到"单文档级" | 三视图切换、**可保存筛选视图**、搜索自动补全 |
| **Mayan EDMS** | 企业级 | 2011 年至今，政府/银行在用，审计完备 | 页面级可逆变换 + 登录尝试审计日志 |
| **Teedy** | 轻量全能 | 百万文档压测过，部署简单 | **嵌套标签**（层级化，标签多了不乱） |
| **Docspell** | 智能分类 | NLP 自动打标是看家本领 | **从已有标注中学习**（我们的标签就是现成训练集） |
| **Papermerge** | 桌面体验 | 界面接近桌面文件管理器 | **双栏拖拽导入** |
| **fapiao-manager-v2** | 国内同类 | 纯本地、无第三方 API 费用，PaddleOCR 结构化识别 | **编辑时实时预览原 PDF**；暴露了国内同类普遍只有"发票"单一场景 |

**共同短板**：多数依赖 Tesseract + Docker 多组件，**中文票据识别一般、部署重、老机器跑不动**。

**差异化定位**：`RapidOCR 中文优化 × 单进程零外部依赖 × 老硬件可跑 × 全中文界面 × 多用户文档可见性`——正好卡在它们的缺口上。

### 7.2 落地选择：只做"纯前端 + 轻接口"的三项

**筛选标准**：优先摘取**不触碰 OCR 管线**、投入产出比最高、在 2 核机上不增加内存压力的能力。

| # | 能力 | 借鉴来源 | 做法 | 效果 |
|---|---|---|---|---|
| 1 | **搜索自动补全** | paperless-ngx / Teedy | 新增 `/api/suggest`，返回标签 + 文档标题候选（**私密文档只对本人/管理员出现**）；前端 180 ms 防抖浮层；点标签候选直接按标签筛选 | 中文找公司名/单据类型从"打字试错"变为"点一下" |
| 2 | **可保存筛选视图** | paperless-ngx / Docspell 书签 | 搜索词 + 标签 + 状态组合存 localStorage，侧栏「保存的视图」一键应用/删除 | 高频查询组合（如"本月发票"）一键直达 |
| 3 | **批量标签** | paperless-ngx 批量编辑 | 批量模式多选卡片 → 统一加/移除标签；后端**逐一校验编辑权限**，私密/只读的自动跳过并提示跳过数量 | 标签体系调整不再逐份点；越权尝试被静默拦截并告知 |

> 4–8 名（审计日志、学习式自动打标、双栏拖拽导入等）留到服务器迁移、算力宽裕后做。

### 7.3 作用与预期效果

浏览器端到端实测三功能全通过、**0 页面报错**；预期让"找文件"和"整理文件"两条高频动线显著变短。

## 八、开源前脱敏与可移植化改造

### 8.1 动机

要把项目公开到 GitHub，就必须先回答两个问题：**① 仓库里有没有不该公开的真实信息？② 换一台机器 clone 下来能不能跑？**

### 8.2 脱敏：逐类清理

| 类别 | 处理前 | 处理后 |
|---|---|---|
| 真实公司主体名（样例素材、默认标签规则、测试关键词） | 多处 | 统一替换为**虚构主体**（星海电子科技 / 蓝盾检测技术 / 汇通财务咨询 / 广诚仪器设备） |
| 真实人名、身份证号、手机号 | 样例与测试文件 | 张三/李四/王五 等虚构名 + 明显假号 |
| 内网 IP | 说明文档含真实网段 | 统一改为示例网段 `192.168.1.100` |
| 本机绝对路径（含系统用户名） | 测试脚本硬编码 | **改为基于脚本位置的相对路径**（`__dirname` / `__file__`） |
| 测试口令 | 复用同一口令 | 中性化为演示口令 |
| 业务强绑定措辞 | 与特定行业强绑定的表述 | 泛化为通用行业表述 |

**样例素材直接重新生成**：`tools/make_samples.py` 改为输出到项目根 `samples/`，主体名全部虚构化后重新渲染 4 张图 + 2 份 PDF（无文本层 / 有文本层各一），保证演示链路真实可跑。

### 8.3 可移植化：把"机器相关"从代码里挤出去

**问题**：原代码把数据目录默认写成 `E:\paperless-lite-data`、启动脚本硬编码虚拟环境解释器路径——这既是信息泄露，也是"换台机器就跑不起来"的根因。

**做法**：引入**三级配置解析**，机器相关配置外置到不进版本库的 `local_settings.py`：

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | 环境变量（`PAPERLITE_DATA` / `PAPERLITE_PY` / `PAPERLITE_PORT` / `PAPERLITE_HOST`） | 临时覆盖、服务化部署 |
| 2 | `local_settings.py`（**已 .gitignore**） | 本机固定配置：数据盘、解释器、备份目录 |
| 3 | 可移植默认值（`<项目目录>/data`、当前解释器） | clone 下来即可跑 |

同时补齐 `.gitignore`：排除数据目录、SQLite 文件、账号文件、本机配置、测试截图与缓存。

### 8.4 作用与预期效果

- 推送前自动扫描 **6 类敏感模式，0 命中**；
- 改动后回归验证：服务正常启动、数据目录仍指向老板本机真实数据、**29 份文档与账号完好**；
- 预期效果：外人 clone 后 `pip install -r requirements.txt && python app.py` 即可跑通；本机使用体验零变化。

## 九、关键 Bug 与根因归档

> 这一节是项目最"值钱"的部分：每个坑都附**根因**，避免下次重新踩。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | OCR 一跑就崩 | 新版 onnxruntime 需要 AVX2 指令集，2011 年 CPU 不支持 | 锁定 `onnxruntime==1.20.1` |
| 2 | 服务"时灵时不灵"，改了代码不生效 | **Windows 的 `SO_REUSEADDR` 允许多个进程同时监听同一端口**，反复重启后积累僵尸实例，请求被随机分发到新旧进程 | 重启前循环 `netstat` + `taskkill` 直到监听数为 0，再启动唯一实例 |
| 3 | `/api/documents` 偶发 500 | 多线程共用一条 SQLite 连接，cursor 混用导致返回行退化成 tuple | 改为**每线程一条连接**（thread-local），WAL 保证并发安全 |
| 4 | 界面上筛选结果被"刷新"掉 | 页面初始化请求与用户操作请求竞态，慢响应覆盖了筛选结果 | 请求序号防护，只接受最新一次响应 |
| 5 | 服务跑一段时间无声消失 | 后台会话回收进程 | 增加 `服务守护.py`（崩溃自动重启）；日常改用双击 `启动服务.pyw` 在自己控制台运行 |
| 6 | 老库升级时建索引报 `no such column: owner` | `owner` 列是由后面的 `ALTER TABLE` 补上的，索引却写在建表脚本里先执行了 | 索引创建移到迁移之后 |
| 7 | **按钮设了 `hidden` 却依然显示** | `.btn` 类里写了 `display:inline-flex`，**显式 display 覆盖了 HTML `hidden` 属性**（UA 默认 `display:none`）的优先级 | 全局补 `[hidden]{display:none!important}`；这类"后端状态正确、DOM 属性也在、元素却可见"的现象，第一反应就该查 CSS 覆盖 |
| 8 | 防火墙规则"添加成功"但没生效 | `netsh` 在受限环境中**静默失败**（退出码 0、无输出、规则未创建） | 改用 PowerShell cmdlet `New-NetFirewallRule`，并回读 `Get-NetFirewallRule` 校验数量 |
| 9 | 库文件明明改了，服务读到的还是旧的 | 配置文件解析顺序未定义（环境变量 vs 硬编码默认值） | 明确三级优先级并文档化（见第八节） |

**方法论沉淀**：① 后端状态正确时，先怀疑前端的样式/属性覆盖；② 命令"成功但无效果"时，必须**回读状态校验**，别信退出码；③ 涉及端口、进程、防火墙的环境问题，先查"是否有多个实例/是否有静默拦截"。

## 十、性能与资源约束下的工程决策

目标机器：**2 核 CPU / 3.9 GB 内存 / 无 GPU**。所有设计都必须在这个预算内。

| 决策 | 替代方案 | 为什么这样选 |
|---|---|---|
| 进程内 `queue` + 工作线程跑 OCR | Celery + Redis | 省掉两个常驻进程，直接省下数百 MB |
| SQLite FTS5 | Elasticsearch / Postgres FTS | 零外部服务；trigram 已满足中文子串检索 |
| RapidOCR + onnxruntime CPU | PaddleOCR 全量 / GPU 推理 | 纯 pip、无系统依赖；本机可接受的单页耗时 |
| OCR 只在必要时触发 | 一律 OCR | 有文本层的 PDF 直取文本，快一个数量级 |
| 缩略图落盘缓存 | 每次实时渲染 | 列表滚动只读小图，避免重复解码大图 |
| 上传进度单请求轮询 | 每文档一请求 | 避免请求风暴（见第三节） |
| 数据目录放非系统盘 | 默认用户目录 | 系统盘紧张（剩余不足 30 GB），且文档持续增长 |

**已知边界（必须如实告知使用者）**：3.9 GB 内存下**多人并发 OCR 会卡**；如需支撑小团队，应迁移到内存 ≥ 4 GB 的专机（代码无需改动，见第十一节）。
